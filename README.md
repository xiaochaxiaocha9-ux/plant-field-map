## 使用

输入编号可定位一株或多株，白色定位圈不会覆盖处理颜色。左右拖动平移摄像机，视角方向保持不变；上下拖动绕平行于台阶长边的水平轴俯仰，双指或滚轮缩放。一次拖动按起始方向锁定为平移或俯仰，减少斜拖误操作。底部切换片区，复位按钮返回当前片区默认视角。点击“保存PNG”生成当前视角图片；电脑可下载，微信内可尝试长按图片保存。微信内兼容性和大陆网络可达性仍需现场实机确认。

手机端优先显示当前待办、搜索命中和选中盆的编号；放大后有空间再显示其他编号，拥挤时保留高优先级标签。“左／中／右”可快速查看对应区段。异交母本和父本均红色，人工自交黄色，自主自交绿色，自然开放白色，测量蓝色；同株多项任务可有多个颜色圈。搜索定位圈与处理颜色分开，PNG按可见标签导出。

点选盆后可直接按花号或植株测量任务勾选完成；也可以在下方清单操作。未完成项按一区从右到左、二区从左到右排列，已完成项移至底部。原始指令保留在展开区。短花号优先使用每日任务的 `flowerId`；不以F0母株花色推断F1，未知花色不猜测。

## 队员反馈（无需AI或云端）

页面阶段显示为“具体日期＋授粉前处理”和“具体日期＋授粉处理”，分别对应保留的 `evening`、`morning` 字段。日期取自任务批次，前处理为开放日前一天。前处理只用“红线 · 去雄套袋”“绿线 · 套袋”等短标签；父本和摘取测量花仍列入清单，只写“不处理”，不自动视为已完成。不处理条目不提供完成按钮，也不会改变授粉任务的完成状态。单花供多朵母花时，清单突出总数并逐一列出供受花号，完成按钮注明“X朵均完成”；示意图同时绘制对应的多条箭头，按具体父本花号分组，以不同弧度与落点错开。点击某朵花的任务会定位该花对应关系，不与同株其他花朵混用。原始每日任务数据不因界面改名而改变。

每朵花、每个阶段分别勾选完成，可记录花冠横径和纵径、茎直径和茎长（均为毫米）、现存真叶数、分枝数、备注及实际处理；均为选填，输入自动保存在本机。处理人和处理日期不再显示，旧版已保存的数据仍保留。清单顶部放置“添加新花苞／花朵”按钮；新增条目追加在原清单之后，默认收起，点击展开填写，刷新、切换阶段和完成其他任务时不会自动展开。收起标题显示已填编号及简短处理，便于多条查找。花苞处理选项使用“红线 · 去雄套袋”“绿线 · 只套袋”等短名称，底层保存的完整处理和旧反馈不重写。新增条目只作现场补充，不自动推定已开放或写入总表。各阶段另有独立总备注，可随反馈一起复制。完成仅表示队员自报执行，不代表受精或坐果成功。历史批次只读。

反馈仅在访问者当前浏览器本地保存，不上传GitHub，不在队员之间同步。队员操作后点“复制反馈”，通过微信发给负责人，再由负责人交给维护总表的会话核对入表。浏览器禁止自动写剪贴板时可长按文本手动复制；未列出的任务不视为完成。原有自由文本和实际时间仍保留在旧记录中，不会因界面简化被丢弃。

反馈按具体日期、处理阶段和片区组织，同株多朵分行，只输出已登记的实际处理、测量和备注等内容。维护会话仍按“批次日期＋植株序号＋花序号＋阶段”识别记录；授粉前处理对应原晚间，授粉处理对应原早间，不能合并两个阶段的完成状态。明确填写的实际操作时间优先；否则依负责人授权采用网页登记时间，并注明来源。总备注不自动转化为任何花朵的已完成记录。若网页提示计划已变化，先核对，不直接覆盖总表；不得据勾选完成补填受精成功、坐果或未报告的测量值。

本网站不含队员上传入口、账号系统或后台数据库。视角、选择和未发送的反馈只保存在访问者自己的浏览器；反馈通过队员手动复制分享。仓库及网页公开，不上传完整实验工作簿、现场照片、精确地址或其他实验材料。

## 维护

- `src/plant-field.html`：三维场景与交互源码。
- `src/daily-tasks.json`：当天已确认的处理任务；空数组表示尚未发布任务，不能把旧任务当作当天任务。
- `docs/index.html`：独立网页发布文件，无外部CDN脚本依赖。
- GitHub Pages 来源为 `main` 分支的 `/docs`，以后更新不需要更换网址。

每日任务由负责人在本地更新、重新构建后提交发布。花朵任务保留 `area`、`id`、`flower`、`evening`、`morning`，新任务尽量附真实 `flowerId`（如 `157-B7`）。868与868（2）不能合并：任务 `id` 推荐用 `868(2)`，全角输入也会规范化；亲本和花号须使用对应的完整编号，不得将两株混用。无具体花朵的植株测量任务可用 `recordType: "plant"`、`flower: ""`，`morning` 写明测量内容；不要虚构花序号或给此记录赋 `flowerId`。已关联具体花朵的授粉和测量仍使用原花号，不能拆成虚构授粉任务。编号必须已录入盆位；异交供受双方仍须核对父母本与花号。

`date`为北京时间的预计开放早晨日期，晚间为前一日；`label`必须写出这两个具体日期及“仅展示已录入盆位的X/Y株”。`flower`为本株累计第几朵，供受粉描述同时写出对应亲本第几朵。同一批次早晨反馈应合并更新原批次；明确取消的项目移除，某时段完成则将该时段描述以“已完成：”开头。前端按各自时段判断待办，不以早晨的处理类别代替晚间执行状态；历史批次不作为今日待办。处理色独立于搜索定位圈。

发布前运行构建与测试，核对已嵌入的数据、日期、覆盖数、花号、两时段状态及双向异交关系。`scripts/task-data.cjs`验证结构、盆位和供受粉花号，同一父本花最多供两朵母花；实验来源资格仍由私有实验记录核验，不把完整研究数据提交到公开仓库。推送后还须核对Pages部署与公开网址返回内容，不能把本地构建或推送成功当作网页已经更新。

补盆位不自动补处理。例如原批次写“父本886盆位未录入”，本轮补齐886位置后，显示改为“父本已定位”，并提示“供粉条目待同步”，但不杜撰886的供粉任务或更改原JSON。验证器仅对带原有“父本盆位未录入”标记、后来获得位置且尚无父本行的记录提供兼容警告；缺失标记、已有但不匹配的对照行仍报错。任务批次说明以原发布内容保留，并明确是发布时记录。日常任务维护者下次更新该批次时应同步新盆位覆盖、父本操作与说明。

构建需要 Node.js、Python 和本地 visualize 导出器：设置 `VISUALIZE_RENDERER` 指向其 `render.py`，需要时设置 `PYTHON_BIN`，运行 `npm run build`。构建从既有可视化导出独立文档，并将已确认任务嵌入网页，不在队员手机上请求私有文件。

测试使用已安装的 Playwright（可通过 `NODE_PATH` 提供），运行 `npm test`。测试数据仅存在于隔离浏览器，不会写入或发布真实任务。

提交前检查 `git diff`，仅添加本项目文件。`scripts/github-pages.cjs` 只通过 Git Credential Manager 使用现有GitHub登录，凭据不写入源码或文件。不要将任何令牌放入网页或仓库。

## 多会话协作

两个维护会话共享同一个项目和仓库，但不会自动共享聊天上下文。网站界面修改与每日任务更新应按文件分工：界面维护使用 `src/plant-field.html`，日常任务维护使用 `src/daily-tasks.json`，最后都从最新源码重新构建 `docs/index.html`。不要用旧聊天中的可视化副本替换本项目源码，也不要直接手改构建产物。修改或发布前先检查工作区和远端；已有未提交改动时应保留，不重置、不强制推送。源码与任务有新版本时先合并，再构建发布；发布完成后核对远端内容与提交版本一致。
