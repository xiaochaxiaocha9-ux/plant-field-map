## 使用

输入编号可定位一株或多株，白色定位圈不会覆盖处理颜色。左右拖动平移摄像机，视角方向保持不变；上下拖动绕平行于台阶长边的水平轴俯仰，双指或滚轮缩放。一次拖动按起始方向锁定为平移或俯仰，减少斜拖误操作。底部切换片区，复位按钮返回当前片区默认视角。点击“保存PNG”生成当前视角图片；电脑可下载，微信内可尝试长按图片保存。微信内兼容性和大陆网络可达性仍需现场实机确认。

手机端采用小型编号标签，外部保留至少44×44像素透明点击区；避让按点击区计算，不用缩小字号换取密集显示。区段实测长度只控制场景比例，不展示尺寸文字或尺寸线；花盆示意尺寸缩小14%，不更改盆位。完整编号标签（点和数字）仅在对应花盆的上方、下方交错放置，不画引线或中间浮动标签，仍拥挤时再隐藏。选中、搜索命中、配对和当前待办优先显示。搜索定位圈与处理颜色仍分开。手机按钮简写为“存图”“一区/二区”，任务图例只显示当前时段用到的类别；完整批次说明和未定位编号收在底部可展开的任务信息中，选中植株的具体操作不删减。PNG按可见标签外观导出，不画透明点击区。

本网站不含队员上传入口、账号系统或后台数据库。不会收集访问者资料；视角与选择只保存在访问者自己的浏览器。仓库及网页公开，不上传完整实验工作簿、现场照片、精确地址或其他实验材料。

## 维护

- `src/plant-field.html`：三维场景与交互源码。
- `src/daily-tasks.json`：当天已确认的处理任务；空数组表示尚未发布任务，不能把旧任务当作当天任务。
- `docs/index.html`：独立网页发布文件，无外部CDN脚本依赖。
- GitHub Pages 来源为 `main` 分支的 `/docs`，以后更新不需要更换网址。

每日任务由负责人在本地更新、重新构建后提交发布，不由队员自行上传。数据格式为：`date`、`label`、`tasks`；每项任务含 `area`、`id`、`flower`、`evening`、`morning`。编号必须已录入盆位。异交操作使用“接X花粉”和“给X供粉”配对，必须核对亲本与花号。发布脚本不会判定实验上的授粉资格。

`date`为北京时间的预计开放早晨日期，晚间为前一日；`label`必须写出这两个具体日期及“仅展示已录入盆位的X/Y株”。`flower`为本株累计第几朵，供受粉描述同时写出对应亲本第几朵。同一批次早晨反馈应合并更新原批次；明确取消的项目移除，某时段完成则将该时段描述以“已完成：”开头。前端按各自时段判断待办，不以早晨的处理类别代替晚间执行状态；历史批次不作为今日待办。处理色独立于搜索定位圈。

发布前运行构建与测试，核对已嵌入的数据、日期、覆盖数、花号、两时段状态及双向异交关系。`scripts/task-data.cjs`验证结构、盆位和供受粉花号，同一父本花最多供两朵母花；实验来源资格仍由私有实验记录核验，不把完整研究数据提交到公开仓库。推送后还须核对Pages部署与公开网址返回内容，不能把本地构建或推送成功当作网页已经更新。

补盆位不自动补处理。例如原批次写“父本886盆位未录入”，本轮补齐886位置后，显示改为“父本已定位”，并提示“供粉条目待同步”，但不杜撰886的供粉任务或更改原JSON。验证器仅对带原有“父本盆位未录入”标记、后来获得位置且尚无父本行的记录提供兼容警告；缺失标记、已有但不匹配的对照行仍报错。任务批次说明以原发布内容保留，并明确是发布时记录。日常任务维护者下次更新该批次时应同步新盆位覆盖、父本操作与说明。

构建需要 Node.js、Python 和本地 visualize 导出器：设置 `VISUALIZE_RENDERER` 指向其 `render.py`，需要时设置 `PYTHON_BIN`，运行 `npm run build`。构建从既有可视化导出独立文档，并将已确认任务嵌入网页，不在队员手机上请求私有文件。

测试使用已安装的 Playwright（可通过 `NODE_PATH` 提供），运行 `npm test`。测试数据仅存在于隔离浏览器，不会写入或发布真实任务。

提交前检查 `git diff`，仅添加本项目文件。`scripts/github-pages.cjs` 只通过 Git Credential Manager 使用现有GitHub登录，凭据不写入源码或文件。不要将任何令牌放入网页或仓库。

## 多会话协作

两个维护会话共享同一个项目和仓库，但不会自动共享聊天上下文。网站界面修改与每日任务更新应按文件分工：界面维护使用 `src/plant-field.html`，日常任务维护使用 `src/daily-tasks.json`，最后都从最新源码重新构建 `docs/index.html`。不要用旧聊天中的可视化副本替换本项目源码，也不要直接手改构建产物。修改或发布前先检查工作区和远端；已有未提交改动时应保留，不重置、不强制推送。源码与任务有新版本时先合并，再构建发布；发布完成后核对远端内容与提交版本一致。
